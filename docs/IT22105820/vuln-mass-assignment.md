# Security Fix: Mass Assignment in Profile Updates

## 1. Vulnerability Summary
- **OWASP Classification:** A08:2021 – Software and Data Integrity Failures
- **CWE:** CWE-915 (Improperly Controlled Modification of Dynamically-Determined Object Attributes)
- **Affected Components:**
  - `backend/utils/pickFields.js` (new)
  - `backend/controllers/details/student-details.controller.js`
  - `backend/controllers/details/faculty-details.controller.js`
  - `backend/controllers/details/admin-details.controller.js`
  - `backend/controllers/branch.controller.js`
  - `backend/controllers/exam.controller.js`

---

## 2. Symptoms
- **Privilege escalation:** `PATCH /api/admin/:id` and `POST /api/admin/register` saved the whole request body to the database. Sending `"isSuperAdmin": true` turned the account into a super admin.
- **Account takeover:** setting `googleId` in a profile update linked the attacker's Google account to the victim's profile, allowing "Sign in with Google" as that user.
- **Tampering with protected fields:** `employeeId`, `enrollmentNo` and `password` could be overwritten through an ordinary profile update, bypassing the secure ID generator and the password-change flow.
- **MongoDB operator injection:** because `req.body` was passed straight to `findByIdAndUpdate`, keys such as `$set` and `$unset` were executed as database commands. For example, `{"$unset": {"name": 1}}` deleted a branch's name.
- **Query operator injection:** object values such as `"email": { "$ne": null }` were accepted as field values and could reach database queries.

---

## 3. Root Cause
- Controllers built the database document directly from untrusted input using `{ ...req.body }`, `Model.create(req.body)` and `findByIdAndUpdate(id, req.body)`.
- The code relied on the frontend form to send only the expected fields. Attackers do not have to use the form; they can send any JSON they want.
- The existing protection was a **blocklist** (`delete updateData.googleId`) in the student controller only. Blocklists miss anything not listed, such as `isSuperAdmin`, `$set` or `employeeId`, and the faculty and admin controllers had no protection at all.
- No type checks were applied, so objects and operators were accepted wherever a simple value was expected.

---

## 4. Architectural Solution Implemented

### Pillar 1: Centralized Allowlist Helper
- Created `backend/utils/pickFields.js` with:
  - `pickFields(source, allowedFields)` copies **only** the listed fields from the request body.
  - `pickProfileFields(body, allowedFields)` does the same, and also accepts the nested `emergencyContact` object, restricted to `name`, `relationship` and `phone`.
- Any field that is not on the list is silently dropped, including operator keys such as `$set` and `$unset`.

### Pillar 2: Primitive-Only Values
- A field is copied only if its value is a string, number or boolean.
- Objects such as `{ "$ne": null }` or `{ "$gt": "" }` are rejected, so they can never reach a MongoDB query or update.
- The helper works with `multer`'s null-prototype `req.body` for multipart form uploads.

### Pillar 3: Per-Model Allowed Field Lists
- Each controller declares the fields it accepts next to the code that uses them:

| Controller | Allowlist constant | Accepted fields |
|---|---|---|
| Student | `STUDENT_PROFILE_FIELDS` | firstName, middleName, lastName, email, phone, semester, branchId, gender, dob, address, city, state, pincode, country, status, bloodGroup, emergencyContact |
| Faculty | `FACULTY_PROFILE_FIELDS` | firstName, lastName, email, phone, address, city, state, pincode, country, gender, dob, designation, joiningDate, salary, status, bloodGroup, branchId, emergencyContact |
| Admin | `ADMIN_PROFILE_FIELDS` | firstName, lastName, email, phone, address, city, state, pincode, country, gender, dob, designation, joiningDate, salary, status, bloodGroup, emergencyContact |
| Branch | `BRANCH_FIELDS` | name, branchId |
| Exam | `EXAM_FIELDS` | name, date, semester, examType, totalMarks |

- The lists are applied to **both** create (register) and update operations.

### Pillar 4: Server-Managed Fields Are Never Client-Controlled
- The following fields can no longer be set from a request body:
  - `isSuperAdmin` (privilege flag)
  - `googleId` (only set by the verified Google login flow)
  - `password` (only changed through `change-password`, which needs the current password, or the email reset flow)
  - `employeeId`, `enrollmentNo` (only generated by the secure ID generator)
  - `profile`, `timetableLink` (only set from the uploaded file name)
  - `_id`, `createdAt`, `updatedAt`
- The old password and enrollment-number handling inside the profile update controllers was removed, since those fields can no longer arrive there.

---

## 5. Verification
The same end-to-end script (temporary MongoDB database, real routes, real login) was run against the old code (`develop`) and against this fix.

| Test | Before (develop) | After (this fix) |
|---|---|---|
| Admin update with `"isSuperAdmin": true` | escalated to super admin | **ignored** (`isSuperAdmin=false`) |
| Admin update with `"$set": { "isSuperAdmin": true }` | escalated to super admin | **ignored** |
| Admin update with `googleId` | overwritten | **ignored** |
| Admin update with `employeeId: 1` | changed 1001 → 1 | **ignored** (still 1001) |
| Admin update with `password` | password replaced | **ignored** (old password still works) |
| Admin register with `isSuperAdmin`, `googleId` | stored | **ignored** |
| Student update with `enrollmentNo`, `email: {"$ne": null}`, `$unset` | rejected by email format check | **ignored** |
| Branch update with `{"$unset": {"name": 1}}` | name deleted | **ignored** (name kept) |
| Admin update with allowed field `firstName` | 200 | **200**, applied |
| Admin edits student incl. `emergencyContact` | 200 | **200**, applied |

**Overall result (both vulnerabilities):** 11/31 checks passed on `develop`, **31/31** pass on this branch.

---

## 6. Known Limitations
- Admins can no longer set another user's password or enrollment number through the profile update API. The frontend never used this; passwords are changed through the dedicated password flows.
- When a new field is added to a model, it must also be added to the matching allowlist, or it will be silently ignored. This is intentional: new fields are safe by default.
- The public `POST /api/admin/register` route is tracked separately as Vulnerability 1 (`fix/admin-creation-and-crypto`); only its mass-assignment issue is fixed here.

---

## 7. Software Engineering Fundamentals Applied
- **Allowlist over Blocklist:** controllers list what they accept instead of trying to remove known-bad fields, so unknown attacks are blocked by default.
- **Secure by Default:** new or unexpected fields are dropped unless someone deliberately allows them.
- **Input Validation at the Boundary:** type checks (primitives only) happen before any data touches the database.
- **DRY / Single Source of Truth:** one `pickFields()` helper is reused across five controllers instead of repeating filtering logic.
- **Separation of Concerns:** each controller owns its own list of writable fields, kept next to the code that uses them.
